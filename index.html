01

The probe that never ran

Four clean results. All of them true. None of them meaning anything.

Section divider. Two seconds on screen. Do not read it aloud.

The question

Does Android ever report a UI node as hidden?

It matters, because if it does, the tool has to filter those nodes out of the map it hands an agent. If it never does, that is code I do not have to write.

The method: launch four apps, dump the hierarchy, count hidden nodes.

Rule 01

Any result of “zero” or “no difference” needs a positive control.

Make the measurement report the thing you expect it to find. Then believe the zero.

The probe now asserts that the hierarchy names the app it asked for, before it believes any count at all.

A probe that never ran and a check that silently passes are the same defect in different clothes.

First of the four habits. Say the number of the rule — the audience is collecting them, and you will show all four again at the end.

My clean-stop script reported “clean” while two emulator helpers were running. A check that silently passes when its own input is missing is worse than no check, because it is trusted.

02

Exit 0 is not evidence

Four commands from one family. Four different ways of telling you it failed.

Section divider. This is the densest and most immediately useful act — flag that as you move into it.

There is no convention. None. Not even within one tool family.

command failure text goes to exit caught by $?
adb (device offline)stderr0no
am startstdout0no
uiautomator dumpboth, split0no
pm grant (undeclared)nothing at all0no
adb uninstallstdout1yes
simctl privacystderr0no

Every tool this project drives reports at least some failures while exiting zero — and mostly on stderr, where a naive stdout check never looks.

Read three rows aloud. The audience finds the fourth themselves.

Do not read the whole table. Read adb, am start, and pm grant. The silence in the pm grant row is the one they will remember.

The silent ones

pm grant

For a permission the app never declared: exit 0, no output on any stream, and nothing granted.

simctl privacy

Accepts a bundle id for an app that is not installed, and does nothing. Successfully.

adb uninstall

Reports Success when all it removed was the updates to a system app. The app is still there.

Rule 02

Read the state back. dumpsys package, not the command's opinion of itself.

Where the platform cannot report state back — iOS privacy is write-only — check the precondition before the write instead.

The one that cost most

mobium back >/dev/null 2>&1

there is no “back” command, and there never has been

The shell printed unknown command into /dev/null. The screen did not move. The next step was misdiagnosed as a scrolling problem for far longer than I want to admit — and that redirect was hiding a missing feature, not a failing call.

“2>/dev/null” is a claim that you already know what a failure there means.

The punchline is that it hid a missing feature. The tool could not press back at all, and this redirect delayed finding that out.

An error message is an instruction an agent obeys unconditionally.

unknown ref text=Charles Babbage — run app_map again

The refusal was correct

Inside a WebView the map matches CSS selectors. There is nothing for a text locator to resolve against.

The advice was impossible

Re-mapping can never help — the ref was never stale. Followed literally, it loops forever.

A wrong remedy is worse than no remedy, because it gets obeyed. When you write an error, check that doing what it says could actually fix it.

This is the strongest agentic beat in the deck. A human gives up on bad advice eventually; an agent does not.

03

The test that could not fail

And four witnesses that lied about a feature which was working.

Section divider. This act contains the single most transferable idea in the talk.

Exactly the test a careful reviewer wants to see

TestTruncationCountsCharactersNotBytes

sample := strings.Repeat("日本語のテキスト", 40)

PASS

Labels are capped at 120. The bug would be capping on bytes instead of characters, which mangles any non-Latin script. So I wrote the test. It passed.

Ask the room, rhetorically, what is wrong with this test. Give them three seconds. Almost nobody sees it.

24

bytes per repeat of that string

120

the cap — exactly five repeats

0

ways this test could ever fail

A 120-byte cut lands on a character boundary every single time. The test passes on the broken implementation and the correct one, identically. It was never a test.

Rule 03

Mutate the code and watch the test fail before you believe it.

Also mention: the test asserted the absence of U+FFFD, which malformed bytes do not contain. Two independent reasons it could not fail. Drop this detail if running long.

The last four defects I logged were in the witness, not the feature.

67

WebDriverAgent honors a pause only while the finger is down

68

A WebView cannot witness a drag, and fails exactly at 500ms

69

A move event is not movement — iOS sends them for a stationary finger

70

iOS has no witness for a double tap at all, by any means available

The gesture code was right. Four times in a row, the thing I built to check it was lying. The devices did not reject my answer — they rejected the way I was asking the question.

When a feature and its test disagree, suspect the test first

The one-line takeaway: build the witness before you trust the measurement, and prove the witness can see.

The honest counter-example

One feature went to both platforms, and neither found anything.

In a defect table that is otherwise a column of yes, that is notable rather than reassuring — so it is written down as the exception, with the reason it is plausible.

A record that only contains the times you were wrong is not a record. It is a performance.

If you keep a log like this, keep the clean results in it too. They are how you tell a real finding from a story you enjoy telling.

This slide buys you credibility for everything else. It also pre-empts the sceptic in the Q&A who assumes you cherry-picked.

04

Fixtures, and the password

Every rule I wrote was tuned on apps written by the company that wrote the operating system.

Section divider. This act is fast and is the emotional peak — do not over-explain any of it.

Three real third-party apps, chosen for the code paths they exercise.

Wikipedia

3 defects, first screen

One feed card produced an 876-character label — 91% of the entire map's text, from one of thirteen entries. It began with a span tag.

F-Droid

0 defects

Chosen because it was the same shape as the app that had just broken everything. Shape was the wrong selection criterion.

Aegis

1 defect, and it was bad

Chosen for a single untested code path: it has a password field.

Google writes Google's apps to be accessible. Nobody else is obliged to. A system app is to a real app what a hand-written fixture is to a device.

Rule 04  ·  capture fixtures from devices, and pick the next app for its code path

Pace this at roughly twenty seconds per card. The F-Droid zero matters — it is why the selection rule changed from size to code path.

Aegis, screen one

My tool printed passwords in plaintext.

Android marks the node password="true" and puts the typed value in its text attribute.

I parsed the flag. I read it nowhere.

Every path that surfaces node text now redacts: the length is kept, the value dropped. And the regression fixture's password value is literally PASSWORD-MUST-NOT-APPEAR — so a leak names itself in the failure output.

The single statement slide in the deck. Do not rush it and do not soften it. The fixture naming trick is the practical gift — say it slowly.

Four habits. All cheap. All earned the hard way.

01

Give every negative result a positive control. Show it a thing it must catch, before you trust a zero.

02

Read the state back. Capture both streams. There is no convention about which one carries the error.

03

Mutate, then watch it fail. A test you have never seen fail is a test you have not tested.

04

Capture fixtures from the real thing. When you fix a heuristic, keep a capture that fails under the old rule.
